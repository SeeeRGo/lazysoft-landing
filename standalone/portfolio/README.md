# Переносимое портфолио и админка

Этот каталог — отдельный сайт. Convex, аккаунт Lazysoft, облачные ключи, npm-пакеты и внешняя база для его работы **не нужны**. Нужен хостинг, который выполняет Node.js 24.12+ (ветка 24) и предоставляет постоянный диск с корректными файловыми блокировками SQLite. На одном статическом S3-хостинге админка не работает.

Состав: страницы четырёх категорий, админка `/admin.html`, HTTP API `/api/portfolio`, SQLite в `data/portfolio.sqlite`. В этой базе находятся контент, изображения/PDF, история и состояние доступа. Максимум 40 работ, 100 файлов / 100 МиБ суммарно, один файл до 8 МиБ. Удаление работы не удаляет файл физически: он может требоваться истории.

## Выбранный хостинг: Beget без VPS

Проверено по официальным страницам 08.09.2026:

- [Виртуальный хостинг Beget](https://beget.com/ru/hosting/virtual): тариф Blog — 420 ₽/мес. **при оплате за год**, итого 5 040 ₽; 12 ГБ, 5 сайтов, SSH и SSL. Это не обещание цены при помесячной оплате. Перед заказом проверить итог в корзине, включая домен.
- [Node.js на Beget](https://beget.com/ru/kb/how-to/web-apps/node-js): Node-приложения запускаются через Apache Passenger в окружении Docker. На Ubuntu 22.04 документирована установка официального Node 24.15.0. Старые аккаунты Ubuntu 18.04 не подходят для этой сборки без смены сервера/окружения.
- Docker здесь — внутреннее окружение хостинга. VPS и собственный Docker daemon клиенту не нужны. Наш `compose.yaml` в этом варианте не используется.

**До оплаты** попросите поддержку подтвердить для выбранного аккаунта:

> Нужен один сайт на Node.js 24.15 (node:sqlite), Apache Passenger, Ubuntu 22.04, HTTPS, SSH/SFTP. База SQLite WAL до 100 МиБ хранится в приватном каталоге приложения, вне public_html. Подтвердите постоянство файлов после перезапуска приложения/сервера, поддержку блокировок SQLite на этом диске и доступ Passenger к каталогу. Есть ли дополнительные ограничения RAM/CPU и совместимость Node 24 с вашей версией Passenger? Нужен виртуальный хостинг без VPS.

Работа на реальном аккаунте Beget пока **не проверена**. Поддержка Node по документации не заменяет проверку конкретного сервера и диска. Preflight проверяет операции, но не может доказать сохранность файлов при обслуживании провайдером или корректность всех сетевых файловых систем.

### Расположение файлов

Пример, реальные пути взять из SSH/панели Beget:

```text
portfolio-site/
  .htaccess               ← из beget.htaccess.example, реальные абсолютные пути
  public_html -> app/webroot
  app/
    passenger.cjs
    server.mjs
    hosting.json
    public/               ← HTML/CSS/JS, раздаёт приложение
    webroot/              ← пустой DocumentRoot, только .htaccess
    data/                 ← приватно, НЕ внутри public_html
      portfolio.sqlite
    tmp/restart.txt
```

Не направляйте `public_html` на `app` или `data`: иначе веб-сервер может открыть базу и ключ. Пустой `webroot` позволяет приложению отдавать все страницы с защитными заголовками. Если хостинг требует другую схему DocumentRoot, сначала согласуйте её с поддержкой; не публикуйте приватные файлы ради устранения 403.

### Установка

1. Создать сайт в панели, привязать домен, включить бесплатный SSL. Заказать/проверить актуальное окружение Ubuntu 22.04. Покупка тарифа не автоматизирована.
2. Подключиться по SSH, затем выполнить `ssh localhost -p 222` по инструкции Beget. Установить официальный Node 24.15.0 x64 в каталог пользователя по их инструкции. Открыть общий доступ **только к каталогу Node**, как требует изоляция Beget; не открывать его для `data`.
3. Распаковать комплект в каталог `app`, не в публичный корень. Использовать переносимый архив с данными, если нужно сохранить текущие работы. Один исходный каталог из Git не содержит пользовательской базы.
4. Создать `hosting.json` по `hosting.example.json`: указать свой HTTPS-домен **без завершающего `/` и без пути**. Сайт рассчитан на корень домена, не на подкаталог. Ключ входа туда не помещается.
5. Установить права `700` на `app/data`, `600` на `portfolio.sqlite`; владелец — пользователь, от которого работает приложение. Не использовать `777`. Проверить, что каталог приложения доступен внутри изоляции сайта.
6. Тем же Node, который будет указан в Passenger, запустить из `app`:

   ```sh
   node check-hosting.mjs
   node --test test.mjs
   node manage.mjs reset-key
   ```

   Последняя команда создаёт новый ключ и выводит **путь** к приватному файлу. При повторном запуске старый ключ и все сессии будут отозваны. Использовать на новой установке или для осознанного восстановления доступа, не при каждом обновлении сайта.

7. Настроить `public_html` на `app/webroot`, а `.htaccess` по примеру `beget.htaccess.example`. Подставить полные пути к Node и приложению. Существующий `public_html` с чужими файлами не удалять: сначала сделать копию и согласовать замену. Не применять команды `rm -rf` из сторонних инструкций вслепую.
8. Создать `app/tmp/restart.txt` (или обновить время файла после изменения кода). Passenger сам запустит приложение на первом запросе. PM2, systemd и открытый порт 8080 на Beget не нужны.
9. Проверить `/health`, главную, категории, `/admin.html`. Зайти новым ключом, загрузить тестовую работу, опубликовать, перезапустить Passenger, проверить сохранность. Тестовую работу убрать через админку. Проверить, что `/data/portfolio.sqlite`, `/hosting.json`, `/server.mjs` возвращают 404.
10. Передать клиенту домен, аккаунт хостинга, архив и ключ отдельным приватным каналом. Настроить резервное копирование и проверить восстановление.

## Другие варианты

| Вариант | Совместимость и решение |
| --- | --- |
| Beget, виртуальный хостинг | Основной путь без VPS, при выполнении условий выше. |
| Selectel VPS / облачный сервер | Резервный путь: Node/Docker + постоянный диск + HTTPS. Администрирование ОС остаётся владельцу или исполнителю. |
| Selectel S3 | Подходит для статических файлов и резервных копий, но не исполняет этот backend. Нельзя просто загрузить туда весь комплект. |
| Selectel Managed Kubernetes | Возможен контейнер с постоянным томом, но для одного портфолио считаю это лишними расходами и сложностью; не предлагаю как основной путь. |
| Timeweb Cloud App Platform | **Не размещать SQLite внутри контейнера:** по FAQ файлы удаляются при новом деплое, примонтировать диск нельзя. Понадобились бы отдельная БД и хранилище, то есть другая архитектура. |

Источники: [каталог Selectel](https://selectel.ru/services/), [FAQ App Platform](https://timeweb.cloud/docs/apps/faq). Не путать App Platform с обычным виртуальным хостингом Timeweb: это разные продукты. Тарифы Selectel здесь не фиксируются: итог зависит от диска, IP, резервных копий и выбранной конфигурации.

### Если нужен именно Selectel

Ориентир для начального теста, а не измеренная гарантия производительности: Linux VPS с 1 vCPU, 1–2 ГБ RAM, 10–20 ГБ постоянного диска, публичным адресом. Отдельные PostgreSQL, S3 и Kubernetes не обязательны. Сервер и прочие платные ресурсы этим комплектом автоматически не создаются.

Запуск без Docker:

```sh
HOST=127.0.0.1 PORT=8080 PUBLIC_ORIGIN=https://portfolio.example.com node server.mjs
```

Установить приложение сервисом под отдельным непривилегированным пользователем. Перед ним — Caddy или Nginx с HTTPS и проксированием на `127.0.0.1:8080`. Не открывать 8080 наружу. SSH ограничить ключами/сетевыми правилами, наружу для сайта открыть только 80/443. Обновления ОС и Node, мониторинг диска и бэкапы — обязанность владельца VPS.

Либо использовать `docker compose up -d --build` из каталога комплекта с установленным `PUBLIC_ORIGIN`. **До запуска** создать `data` с владельцем UID/GID 1000:1000 (пользователь `node` в образе), каталог 700, файлы 600. Если там уже есть база, сначала сделать бэкап. Bind mount `./data:/app/data` сохраняет данные при пересоздании контейнера. Dockerfile не включает базу/ключи в образ. `hosting.json` используется только Passenger; Docker/обычный запуск используют `PUBLIC_ORIGIN`.

Поддерживайте актуальную проверенную версию Node 24.x. Локальные тесты выполнены на 24.12.0; встроенный SQLite в ней выдаёт ExperimentalWarning. На хостинге тестировать выбранную версию перед переключением трафика, а не менять major вслепую.

## Доступ и безопасность

- Сессия 15 минут без автопродления; случайный токен в памяти браузера, в БД только его хеш. Корневой ключ не заменяет сессию в API.
- «Выйти» и «Отозвать доступ» завершают **все** сессии единственного администратора. Замена ключа также завершает их. Это не многопользовательская CMS.
- Отзыв, срок сессии и версия повторно проверяются внутри транзакции записи. Одновременные публикации не затирают друг друга молча.
- Общие лимиты сайта: 5 входов/мин, 30 неавторизованных операций/мин, 60 административных запросов/мин, 10 загрузок/мин, 120 чтений API/мин. Сохраняются при рестарте. Это не защита от DDoS; общая квота при атаке может мешать владельцу.
- Только JPG/PNG/WebP/PDF; проверяется сигнатура, размер и принадлежность файла. SVG/HTML не принимаются; PDF отдаётся как вложение. Проверка сигнатуры — не антивирус.
- Файлы опубликованных/ранее загруженных работ не являются приватными документами. Секретные материалы туда не загружать.
- Клиентский текст вставляется через `textContent`, внешние скрипты не подключаются. HTTPS обязателен в production. Не размещать на том же origin чужие или недоверенные приложения.

## Резервные копии и передача

```sh
node manage.mjs backup /absolute/private/path/portfolio-backup.sqlite
```

Используется SQLite Backup API, а не простое копирование одного файла при активном WAL. В копии есть **все изображения, PDF, история, хеш ключа и сессии**: хранить приватно, не в Git и не в `public_html`. Делать ежедневный бэкап через Cron хостинга и перед обновлениями; отдельную копию регулярно скачивать с хостинга. История версий не заменяет бэкап при потере диска/аккаунта.

Восстановление: остановить приложение/отключить его в панели, сохранить текущий `data` целиком как резервную копию; восстановить бэкап в **новый пустой** приватный каталог под именем `portfolio.sqlite`, без старых `-wal`/`-shm`; выставить права; запустить `reset-key` для отзыва восстановленных старых сессий; подключить каталог и проверить сайт. Не подменять БД у работающего процесса.

Для первичной передачи подготовленный архив содержит контент и историю, но **не содержит старый ключ/сессии**. Новый ключ создаётся у владельца. Файл `initial-admin-key.txt`, если создан первым запуском, после ротации ключа не обновляется и может быть уже неактуальным. Потерянный доступ восстанавливается через `node manage.mjs reset-key` по SSH.

Перенос домена: поменять `publicOrigin`/`PUBLIC_ORIGIN`, настроить DNS/SSL, перезапустить. Ссылки API и файлов относительные; URL Convex и старого S3 в приложении нет. Старую версию сайта/Convex отключать только после финального экспорта и проверки нового адреса. Остальные приложения Lazysoft, использующие Convex, не входят в этот перенос.

## Проверки перед окончательным переключением

- Заморозить редактирование старой версии на время последнего экспорта; сравнить версии и количество работ/файлов/истории.
- Проверить сохранность после рестарта и обновления кода, резервную копию и отдельное восстановление.
- Проверить главную, четыре категории, полноэкранный просмотр, контакты и вход на телефоне/десктопе.
- Убедиться в DevTools, что сайт не обращается к Convex или старому хранилищу.
- Проверить 401 после истечения/отзыва тестовой сессии и 404 на приватные пути.
- Только после проверки направлять основной домен. Сохранить предыдущий deployment для отката; новые изменения контента не должны потеряться при откате.
