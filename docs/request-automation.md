# Автоматическая обработка заявок

Текущий способ запуска: **Convex немедленно планирует generation action**, который передаёт конкретный job постоянно размещённому HTTPS executor. Executor вызывает RouterAI и выполняет тяжёлую браузерную проверку, упаковку и публикацию. GitHub Actions не опрашивает очередь и не запускает production-генерацию по расписанию; workflow worker оставлен только как ручной аварийный инструмент. Генерация не зависит от локального Codex, сохранённой авторизации ChatGPT, systemd или процессов рабочего компьютера.

## Целевой сценарий

1. Новая заявка MVP атомарно сохраняется в Convex вместе с заданием на ТЗ и демо. Старые заявки сами в обработку не попадают; CRM и mobile сохраняют текущий ручной процесс.
2. Convex action передаёт job hosted executor; тот забирает lease, вызывает RouterAI, проверяет артефакты, публикует демо в Яндекс Облаке и сохраняет PDF и архив исходников.
3. Клиент получает результат на секретной странице заявки и уведомление по доступному каналу. Сбой доставки не теряет результат.
4. Клиент может один раз отправить список правок. Ограничение проверяется транзакцией Convex, а не только кнопкой. Повторный запуск после технического сбоя не расходует ещё одну правку.
5. После результата клиент может принять демо без правок или дождаться единственного раунда правок. Затем доступны кнопка «Хочу купить исходники за 5 000 ₽» и заявка на доработку от 10 000 ₽ с постоплатой после отдельного согласования. Покупка сейчас ручная: сообщение сохраняется в чате заявки, владельцу отправляется событие в Telegram с контактом клиента. Оплата и передача обсуждаются в чате. Кнопка не списывает деньги и не открывает архив; повторные нажатия не дублируют запрос.
6. Открытие результата, переход к PDF/демо, правки, принятие, начало оплаты, успешная оплата, скачивание и заказ доработки записываются в Convex и уведомляют владельца в Telegram.

## Границы безопасности

Текущий вариант не требует ключей ЮKassa: форма оплаты убрана, HTTP-операция checkout отключена. Старый платёжный модуль и записи сохранены для совместимости; описанные ниже проверки ЮKassa относятся к будущему возврату онлайн-оплаты, а не к ручной покупке.

- Идея клиента — недоверенный ввод. RouterAI не получает контакты клиента, секреты оплаты, Convex, Telegram или облака.
- Генерация выполняется в отдельной директории/контейнере; публикацию и выдачу делает доверенный исполнитель после проверки результата.
- Архив исходников хранится приватно. Публичное демо не содержит архив, ключи, контакты или секретную ссылку заявки.
- Подтверждение оплаты берётся из серверного GET к API ЮKassa с проверкой суммы, валюты, магазина, идентификатора заказа и режима test/live. Возврат браузера и тело webhook не подтверждают оплату.
- Дубли запросов, webhook и завершения задания не создают повторной выдачи. У задания есть аренда с идентификатором попытки: опоздавший исполнитель не может заменить новый результат.
- Демо показывает интерфейс и сценарии с демонстрационными данными. Оно не обещает готовую промышленную систему; состав работ, интеграции и внешние расходы фиксируются в ТЗ.

## Внешние настройки для сквозного запуска

- Постоянно доступный HTTPS executor и ключ RouterAI; процесс на рабочем компьютере не нужен.
- Яндекс Облако: отдельное место для демо и права публикации. Не размещать клиентский код на origin лендинга с его секретными страницами.
- ЮKassa: `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, тестовый магазин для первого платежа; настройки чеков магазина.
- Доставка клиенту: SMTP для email; Telegram-бот может отправить личное сообщение только известному chat_id после начала диалога клиентом. Произвольный @username и телефон MAX сами по себе не дают боту права доставки. Страница заявки остаётся постоянным местом результата.

## Проверки до включения

- Реальная тестовая заявка → RouterAI → доступные PDF и демо → сообщение на странице.
- Два параллельных запроса правок создают ровно одно задание; повторное завершение не дублирует сообщения.
- Тестовая оплата 5 000 ₽; поддельный webhook, неверная сумма и неоплаченный запрос не открывают архив.
- До оплаты исходники не присутствуют в API, HTML или публичном каталоге.
- Реальное событие доработки доходит владельцу; недоставленные уведомления видны и повторяются.
- Визуальная проверка страницы на 390, 768, 1024 и 1366 px с заполненными результатами.

## Состояние внедрения

Production-контур включён 19 сентября 2026: Convex `fearless-gnu-184` dispatch-ит
jobs в Yandex Serverless Container `lazysoft-generation-executor`. Контейнер
работает с `concurrency=1`, 2 vCPU, 2 ГиБ RAM и timeout 3600 секунд. Входящий
`/generate` публично доступен для Convex, но требует отдельный
`X-Lazysoft-Executor-Token`; стандартный `Authorization` не используется, потому
что его перехватывает IAM Yandex Cloud.

- Реализованы транзакционная очередь, аренда задания, повторные попытки, один раунд правок, приём результата, приватный архив, оплата через API ЮKassa, события владельцу, очередь доставки и привязка Telegram/MAX.
- Реализован исполнитель `automation/worker.mjs`: структурированная двухэтапная генерация через RouterAI, отдельная генерация изображений, проверка CMS и браузерная приёмка, публикация статического демо в Yandex Object Storage, сохранение PDF и ZIP в Convex. Инфраструктурных секретов у модели нет.
- Convex планирует dispatch сразу при создании initial/revision job и повторяет его с backoff при недоступности executor. `.github/workflows/request-worker.yml` не имеет расписания и используется только вручную при аварийном восстановлении.
- Проходят 14 автоматических тестов, TypeScript и сборка Astro. Проверены повторные клики, аренда, приватность архива, платёжные атрибуты, поддельный webhook, привязка чата, создание PDF и запрет symlink в демо. Дополнительно проверены возврат к оплаченному заказу без повторного перехода на checkout и восстановление статуса после сбоя последней попытки доставки.
- После возвращения из ЮKassa страница повторно сверяет оплату через сервер. Есть отдельная кнопка проверки; при временной ошибке платёжного сервиса сама заявка остаётся доступной.
- Локальная вёрстка страницы результата проверена на 390/768/1024/1366 px без переполнения и наложений. Проверка выполнена с тестовыми данными, не с реальной оплаченной заявкой.
- Новые функции и схема опубликованы в production Convex. Реальная заявка `#1f029af4` перешла `queued → running` через Convex → Yandex executor; heartbeat подтверждён. Полное завершение этой генерации и доставка результата проверяются отдельно.
- Не проверены после перехода: полный Convex → Yandex executor → RouterAI → публикация прогон до terminal status, SMTP/MAX-доставка и подтверждённый тестовый платёж.

## Настройки по местам

| Где | Переменные |
| --- | --- |
| Convex | `REQUEST_AUTOMATION_ENABLED`, `REQUEST_DEMO_ORIGIN`, `AUTOMATION_WORKER_SECRET`, `REQUEST_GENERATION_EXECUTOR_URL` |
| Convex, для ЮKassa | `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_MODE=test`, `YOOKASSA_VAT_CODE` согласно налоговым настройкам магазина |
| Convex, SMTP | `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` |
| Convex, Telegram | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` владельца, `TELEGRAM_BOT_USERNAME` без @, `TELEGRAM_WEBHOOK_SECRET` |
| Convex, MAX | `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `MAX_WEBHOOK_SECRET` |
| Convex и deploy workflow с одинаковым значением | `DELIVERY_ENCRYPTION_KEY`: 32 случайных байта в hex (64 символа) для AES-256-GCM |
| Yandex executor | `AUTOMATION_WORKER_SECRET`, `ROUTERAI_API_KEY`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `CONVEX_SITE_URL`, `REQUEST_DEMO_BUCKET`, `REQUEST_DEMO_ORIGIN` |

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в GitHub уже были, но секреты GitHub не копируются автоматически в Convex. Переменная `DELIVERY_ENCRYPTION_KEY` передаётся лендингу workflow деплоя. До её настройки новая заявка не содержит зашифрованной ссылки для исходящей доставки; не включать автоматический поток до настройки.

Локальная проверка наличия настроек без обращения к очереди:

```sh
node --env-file-if-exists=.env.automation automation/worker.mjs --check-config
```

Hosted executor содержит AWS CLI, Chromium и zip. GitHub workflow не имеет расписания и остаётся только ручным аварийным инструментом. Локальный постоянно работающий исполнитель не используется.

## Webhook

На собственном домене Convex (`CONVEX_SITE_URL`):

- ЮKassa: `/yookassa-webhook`, события `payment.succeeded` и `payment.canceled`. Обработчик перепроверяет платёж серверным запросом.
- Telegram: `/telegram-request-webhook`, `secret_token` совпадает с `TELEGRAM_WEBHOOK_SECRET`, update `message`. Перед установкой проверить `getWebhookInfo`: нельзя перезаписать обработчик другого действующего сценария без объединения.
- MAX: `/max-request-webhook`, `secret` совпадает с `MAX_WEBHOOK_SECRET`, update `bot_started`. API-домен по актуальной документации — `platform-api2.max.ru`; проверить доверенную TLS-цепочку из среды Convex.

Клиент на секретной странице видит ссылку `start` своего бота. После запуска в личном диалоге webhook связывает chat/user ID с заявкой, проверив хеш секретного токена. Привязать уже подключённую заявку к другому ID нельзя. Простое имя или номер телефона из формы не используются как бот chat ID.

## Порядок включения

1. Настроить секреты dev и тестовый магазин. Выделить отдельный origin демо (не origin лендинга) и bucket с доступом на чтение демо; исходники туда не загружаются.
2. Настроить секрет RouterAI и запустить одну искусственную заявку в dev через `workflow_dispatch`.
3. Проверить PDF, работающий интерфейс демо, реальную отправку результата и один раунд правок.
4. Пройти платёж в тестовом магазине, проверить webhook, запрет скачивания до оплаты и доступ после.
5. Проверить все уведомления владельцу, включая ошибки доставки.
6. Опубликовать проверенную версию и настроить production-секреты. Включить флаги обработки только после проверки. Старые заявки не ставятся в очередь автоматически.

При сбое приостановить GitHub variable и Convex env `REQUEST_AUTOMATION_ENABLED`; сохранить задания и результаты для диагностики. Флаг блокирует новые захваты, но уже начатый GitHub job нужно отменить в Actions отдельно.
