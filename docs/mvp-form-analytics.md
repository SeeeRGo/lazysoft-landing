# Аналитика заявки на разбор идеи

Форма на `/sayt-po-idee/` отправляет технические события в Яндекс Метрику. Текст идеи и сам контакт в аналитику не передаются: они отправляются владельцу сайта через сервер только после успешной отправки формы.

## Основная воронка

| Событие | Что означает |
| --- | --- |
| `mvp_landing_view` | Открыта страница предложения |
| `mvp_brief_started` | Пользователь впервые начал заполнять форму |
| `mvp_brief_form_completed` | Сервер подтвердил сохранение заявки |
| `mvp_request_submitted` | То же успешное действие с параметром выбранного канала |
| `mvp_request_page_opened` | Посетитель открыл приватную страницу своей заявки |
| `mvp_request_message_sent` | Посетитель отправил уточнение со страницы заявки |

Существующие цели `mvp_brief_started` и `mvp_brief_form_completed` сохранены, поэтому их не нужно пересоздавать в Метрике. Старые цели шагов формы, скачивания PDF и переходов к контакту больше не используются новой страницей.

## Диагностика

- `mvp_request_field_started` — начато заполнение `idea` или `contact`;
- `mvp_request_contact_method` — выбран `telegram`, `email` или `max`;
- `mvp_voice_input_used` — идея успешно продиктована;
- `mvp_direct_contact_clicked` — переход к прямому контакту с параметром `channel`;
- `mvp_request_validation_error` — идея или контакт не прошли проверку;
- `mvp_request_submit_failed` — сервер не смог доставить заявку.

В Директе основной целью должна быть `mvp_brief_form_completed`. На странице сайта событие срабатывает после подтверждения сохранения заявки в Convex; Telegram доставляется отдельно с повторами. Один клик по кнопке не считается конверсией.

## Доставка заявок

В GitHub Actions → Settings → Secrets and variables → Actions → Repository secrets должны быть добавлены:

- `TELEGRAM_BOT_TOKEN` — токен Telegram-бота;
- `TELEGRAM_CHAT_ID` — идентификатор чата, куда бот присылает заявки;
- `CONVEX_DEPLOY_KEY` — ключ production deployment для публикации функций;
- `CONVEX_INGEST_SECRET` — секрет серверной записи заявок.

В Repository variables должна быть задана `CONVEX_SITE_URL` — адрес HTTP Actions production deployment.

После настройки отправьте тестовую идею с UTM-метками и проверьте одновременно сообщение в Telegram и достижение цели `mvp_brief_form_completed`.

Каждая заявка также резервно записывается в таблицу `mvpRequests` в Convex. Новая заявка получает две разные секретные ссылки: посетитель видит `/request/`, а владелец получает `/request-admin/` в Telegram. На странице управления можно отправить сообщение, ссылку на PDF, ссылку на демо и изменить статус. При ответе посетителя приходит отдельное уведомление в Telegram.

В базе хранятся только SHA-256-хеши ключей доступа. Публичных Convex-функций чтения нет: браузер обращается к серверу сайта, а тот — к защищённым HTTP Actions. Секретную ссылку посетителя нельзя публиковать: любой, у кого она есть, сможет прочитать переписку и написать сообщение.


## Перепроверка Telegram — 15 сентября 2026

Сервер production и Convex подключены к одному боту `@lazysoft_mvp_idea_bot`
и одному чату владельца. Проверены `getMe`, доступ к чату и `getWebhookInfo`: ошибок
и ожидающих обновлений нет. Все 7 имеющихся записей `requestEvents` имеют `notifiedAt`;
это история доставки, а не новые тестовые отправки.

На публичной странице посещения, заполнение полей и переход к прямому контакту
отправляются в Метрику. После отправки формы владелец получает Telegram-уведомление.
На приватной странице заявки события просмотра, открытия демо, выбора версии,
доработки и запроса покупки записываются в Convex и доставляются через очередь
с повторными попытками и защитой от дублей. Публичные примеры не создают заявки.

Уведомление о сообщении посетителя в чате заявки теперь ожидается до ответа HTTP,
чтобы serverless-контейнер не приостановил незавершённую отправку. Проверены задержка
и отказ Telegram через локальную заглушку. Реальные сообщения ради проверки не отправлялись.

С 16 сентября 2026 новая форма сайта передаёт стабильный ключ отправки. Уведомления о получении заявки и запуске генерации — отдельные серверные события `request_received` и `generation_started`; они относятся к Telegram, а не к целям Метрики.


### Генерация без контакта (17 сентября 2026)

`/sayt-po-idee/` содержит только идею и кнопку генерации. Начало заполнения и отправка по-прежнему используют `mvp_brief_started`, `mvp_request_field_started`, `mvp_brief_form_completed`, `mvp_request_submitted`; для новых заявок параметр `contactMethod` равен `none`. События выбора контакта на первом экране больше не возникают.

На `/request/` кнопка «Хочу купить» раскрывает условия и контактную форму и отправляет `mvp_purchase_opened` в Метрику. Для отчёта по цели её идентификатор нужно добавить в настройках счётчика. Кнопка раскрытия не создаёт заказ и не означает оплату. Выбор комплекта сохраняет контакт и событие `offer_purchase_requested` одной транзакцией; уведомление получает владелец, а не клиентский бот.


### Цели после упрощения формы — 17 сентября 2026

- `mvp_brief_started`: «Начал описывать идею», ID 593801675 сохранён.
- `mvp_brief_form_completed`: «Отправил идею сайта», ID 593801745 сохранён.
- `mvp_purchase_opened`: «Нажал «Хочу купить»», открытие формы, не оплата.
- `mvp_purchase_requested`: «Отправил заявку на покупку», после успешного ответа API на `offer_purchase_requested`. Контакт и запрос уже сохранены; доставка уведомления владельцу выполняется сервером. Это заявка, не подтверждённая оплата.

Новое событие передаёт только `demoId`, `hosting`, `purchase`, `offerVariant`, `contactMethod`. Сам контакт, текст идеи, токен заявки и URL с секретом в параметры события не включаются. Ошибки API и невалидная форма не создают это достижение; повторная отправка уже принятого выбора блокируется локально. `mvp_request_submitted` остаётся диагностическим дублем отправки идеи.
