# Очередь и публикация в Яндекс Облаке

## Различай два развёртывания

Статические клиентские демо публикуются в Yandex Object Storage. Лендинг,
страница заявки и API работают через Serverless Containers/API Gateway.
Изменение демо само по себе не требует пересборки лендинга, изменения DNS
или запуска `.github/workflows/deploy-yandex.yml`.

Опорные файлы репозитория:

- `deploy/demo-resources.json`, `deploy/demo-bucket-policy.json` — существующие ресурсы.
- `docs/yandex-demo-infrastructure.md` — история их создания.
- `docs/production-automation.md` — эксплуатация и история выпусков.
- `.github/workflows/deploy-yandex.yml`, `Dockerfile` — выпуск приложения Lazysoft.

Исторические заметки не доказывают текущее состояние. Проверь выбранный env,
ресурс и deployment до мутации. Изменения трёх версий на момент создания скилла
проверялись в dev; это не подтверждение их присутствия в production.

## Настройки без раскрытия секретов

Worker ожидает имена переменных:

```text
CONVEX_SITE_URL
AUTOMATION_WORKER_SECRET
REQUEST_DEMO_BUCKET
REQUEST_DEMO_ORIGIN
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
ROUTERAI_API_KEY
```

Production запускается одноразовым GitHub Actions runner. Секреты находятся в
GitHub Actions secrets; не печатай env целиком и не копируй их на рабочий
компьютер. Генерация использует RouterAI API. Локальные Codex-авторизация,
Docker-образ генератора, systemd, `flock` и постоянный worker не используются.

Используются Node, Chromium, AWS CLI и zip/unzip на GitHub runner.

Без запуска очереди:

```sh
npm run worker:once -- --check-config
```

Проверка выводит недостающие настройки, но не доказывает доступ к модели, бакету
или доставке. Для одной разрешённой заявки с фактическим ID:

```sh
REQUEST_WORKER_REQUEST_ID=ACTUAL_REQUEST_ID npm run worker:once
```

Не запускай общий worker без ID ради диагностики: он может захватить чужую заявку.
Штатный ручной запуск выполняй через `workflow_dispatch`; локальный запуск — только
диагностический и требует отдельного явного разрешения на конкретную заявку.

## Выполнение задачи

Backend выдаёт `jobId` и `leaseToken`; lease действует 5 минут, worker продлевает
его каждые 45 секунд. При потере lease прекращает работу. Очередь ограничивает
попытки тремя; не обнуляй счётчик автоматически, чтобы обходить ошибку.

Порядок: захват → генерация → проверка → архивы → публикация новой версии →
HTTPS-проверка → загрузка архивов в приватное хранилище → `complete` → доставка.
Не объявляй задачу готовой до успешной проверки опубликованных ресурсов.
Запуск очереди может инициировать реальные уведомления; используй тестовую заявку
для согласованного сквозного теста.

## Публикация демо

Уже используемый бакет — `lazysoft-request-demos-20260907`; подтверждай значение
через конфигурацию. Публичное чтение отдельных объектов разрешено, листинг закрыт.
Ключ загрузчика ограничен бакетом. Не расширяй права на каталог/облако для обычной
загрузки и не включай анонимную запись.

Каждый выпуск получает новый путь:

```text
https://<bucket>.storage.yandexcloud.net/<jobId>/<random-release>/1/index.html
https://<bucket>.storage.yandexcloud.net/<jobId>/<random-release>/2/index.html
https://<bucket>.storage.yandexcloud.net/<jobId>/<random-release>/3/index.html
```

Используй HTTPS origin из настроек. В текущем worker случайный компонент —
12 байт в hex; `Cache-Control: public,max-age=3600`. Новые пути позволяют
избежать старых файлов в кэше и сохраняют предыдущий выпуск для отката.
Секретность URL не делает объект приватным.

При ручной публикации уже проверенной папки примени тот же принцип через
`aws --endpoint-url=https://storage.yandexcloud.net s3 cp` с `--recursive` и
точным новым префиксом. Не используй `sync --delete` на общем бакете. Архивы,
приватные материалы, контакты и токены в публичный префикс не загружай.

Проверь HTTP-статус и Content-Type страниц и ресурсов, отсутствие принудительного
скачивания HTML. Открой реальные URL в браузере на мобильной и десктопной ширине;
проверь отсутствие ссылок на localhost и ошибок ресурсов. TLS на служебном
HTTPS-адресе хранилища не требует ручного выпуска Let's Encrypt клиенту.

## Если задача включает выпуск лендинга

Сначала проверь изменения, сборку и backend-контракт. Учти: push в `main` запускает
production workflow с деплоем Convex, сборкой контейнера и выпуском в Яндекс.
Проверка dev Convex не заменяет production-деплой; GitHub runner всегда использует
worker из выбранного коммита. Согласуй версии worker и backend перед включением
нового формата результатов. После выпуска проверь фактическую страницу и API.

Для отката демо используй предыдущий проверенный URL. Для отката лендинга —
предыдущий образ/коммит через существующий workflow. Не удаляй данные Convex,
старые клиентские артефакты или чужие облачные ресурсы.
